<a id="web-structure"></a>
## 웹 구조

현재 앱은 `web/`의 Next.js App Router입니다. `web/app/`이 라우트와 정적 문서를 구성하고, `web/src/`에 화면·상태·공통 UI를 둡니다. 게임 데이터 JSON은 TanStack Query로 읽고 UI 상태는 Zustand로 관리합니다.

| 위치 | 책임 |
| --- | --- |
| `web/app/[...slug]/page.tsx` | 포켓몬 상세의 정적 HTML과 메타데이터 |
| `web/src/screens/` | 기능별 화면 |
| `web/src/components/` | 공통 UI와 화면 연결 |
| `web/src/lib/` | 데이터 조회, 계산 보조, 라우팅, API 연결 |
| `web/src/styles/cinema/parts.css` | 재사용하는 카드·버튼·입력·탭 스타일 |
| `web/src/styles/cinema/`의 화면별 파일 | 홈·일정·상세·모달 등의 배치 |
| `frontend-v4/scripts/extract-data.mjs` | Python 산출물을 현재 웹 JSON으로 변환 |

`frontend-v4/`의 Firebase 연동은 이전 앱용입니다. 현재 계정 기능은 `web/src/lib/serverApi.ts`에서 Fastify API를 사용합니다. 상세 문서 생성은 빌드 시 수행하며, 과거 계획의 ISR·BFF를 모두 구현한 것으로 설명하지 않습니다.

<a id="pipeline"></a>
## 데이터 파이프라인

```text
외부 원본 + backend/config 수동 보정
  → scripts/fetch_data.sh
  → backend/*_build.py: 이름·폼 정규화, 순위·일정·도감 계산
  → backend/guard.py: 이전 정상 데이터와 비교
  → dist/data.js 및 부속 데이터
  → web의 npm run data: public/data JSON 생성
  → Next.js 빌드와 정적 자산 배포
```

스프라이트는 `backend/sprites.py`가 준비하고 `web`의 `npm run prepare-assets`가 복사합니다. 원본 실패 시 스냅샷 대체가 가능하지만, 필수 데이터와 정상 대체본이 모두 없으면 빌드를 중단합니다. 대체한 데이터는 stale 상태로 구분합니다.

| 자료 | 사용 목적 |
| --- | --- |
| PvPoke | 리그별 순위·점수·추천 기술, 출시 여부 보조 |
| PokeMiners 게임마스터 | 종족값·기술·상성·CPM·폼 관련 수치 |
| PokeAPI CSV·스프라이트 | 한국어 명칭·폼 매핑·이미지 |
| hawaii 성능표 | PvE 외부 성능 자료. 자체 계산과 구분 |
| ScrapedDuck/LeekDuck | 이벤트·레이드·알 자료 자동 수집 |
| 공식 한국 발표·수동 설정 | 한국 전용 일정과 출시 보정 |

출처별 조건은 [NOTICE](NOTICE.md)를 확인합니다. 한국어 이름이나 미공개 보스를 추정해서 채우지 않습니다.

### 빌드 옵션

| 명령 | 용도 |
| --- | --- |
| `bash scripts/build.sh` | 원본 수집·계산·이미지 전체 준비. 이미지 처리에는 Pillow 필요 |
| `bash scripts/build.sh --data-only` | 이미지 없이 데이터 생성. 웹 CI의 빠른 경로 |
| `bash scripts/build.sh --no-fetch` | 이미 받은 원본으로 다시 계산 |
| `bash scripts/build.sh --meta-only` | 준비된 계산·이미지를 사용해 최종 데이터만 재조립 |
| `bash scripts/build.sh --no-sprites` | 기존 이미지가 있을 때 재사용 |

생략한 단계의 파일이 없으면 먼저 전체 또는 데이터 빌드를 실행합니다. `dist/index.html`을 여는 방식은 현재 앱의 실행 방법이 아닙니다.

<a id="calculation"></a>
## 계산 기준과 해석

다음은 서비스의 계산 가정입니다. 실제 게임의 모든 전투 상황을 재현하는 시뮬레이터는 아닙니다. 수치를 바꿀 때는 구현·검증·화면 설명을 함께 수정합니다.

| 영역 | 기준 | 구현 |
| --- | --- | --- |
| PvE 자체 계산 | 레벨 40, IV 15/15/15, 고정 보스 방어·DPS 가정 | `backend/pve_build.py` |
| D-MAX 티어 | 공격·맥스 기술 위력·자속 기반 비교 | `backend/value_build.py` |
| CP | 공격·방어·체력 IV와 레벨 CPM 적용 | `web/src/lib/cp.ts` |
| 솔플 계산 | 전투 시간과 재진입 손실을 포함한 근사 모델 | `web/src/lib/solo.ts` |
| PvP 팀 | 리그 점수·타입 상성·약점 보완 기반 추천 | `web/src/lib/deck.ts` |

### 주요 산식

```text
피해 = floor(0.5 × 위력 × 공격 / 방어 × 배율) + 1
DPS = (스피드 기술 총피해 + 차지 기술 피해) / 사이클 시간
TDO = DPS × 체력 / (보스 DPS × 100 / 방어)
PvE 종합 점수 = DPS³ × TDO / 1000

CP = max(10, floor((공격+IV) × √(방어+IV) × √(체력+IV) × CPM² / 10))
D-MAX 티어 = round(공격) × 기술 위력 × 자속 배율
```

맥스 기술 위력은 다이맥스 350, 거다이맥스 450을 사용합니다. 티어·딜러·탱커는 서로 다른 지표이므로 같은 필드나 문구로 표시하지 않습니다. 상세 배율과 비교 조건은 각 구현과 아래 과거 계산 결정 기록을 함께 봅니다.

### 알려진 한계

- PvE의 고정 보스 가정 때문에 실제 전투와 내구 평가가 달라질 수 있습니다.
- 맥스가드·맥스스피릿·게이지 운용 전체를 평가하지 않습니다.
- PvP 팀 추천은 실드·기술 사이클 전체를 시뮬레이션하지 않습니다.
- 솔플 보정은 제한된 실측에 기반하므로 특수 보스에서 오차가 생길 수 있습니다.
- 출시 목록·한국 일정의 수동 보정은 반영 지연이 있을 수 있습니다.
- 한국어 이름은 자료 간 표기 차이가 있고, 매칭 실패 시 영문이 남을 수 있습니다.

## 이전 버전의 설계 결정

아래 기록은 v2~v4 당시의 문제·검토·결과를 보존한 자료입니다. 경로·구성·수치는 당시 기준이며 현재 실행 절차로 사용하지 않습니다. 현재 구조는 이 문서 상단을 기준으로 합니다.

<summary>2.1 성능: React로 갈 것인가 (v2.0.0)</summary>

### 2.1 성능: React로 갈 것인가 (v2.0.0)
**문제** — 단일 HTML에 스프라이트를 base64로 인라인하다 보니 3.0MB 한 덩어리가 됐고, 배포도 느려졌다.

**검토** — React/Vue 마이그레이션을 후보에 올렸지만 채택하지 않았다. 데이터가 빌드 타임에 고정되고 상호작용이 "목록 렌더 + 팝업" 수준이라 가상 DOM의 이득이 적고, 런타임 번들이 오히려 초기 전송량을 늘린다. 병목은 렌더링 방식이 아니라 **한 파일에 다 넣은 구조**였다.

**결정** — 프레임워크 대신 산출물 분리: HTML / `data.js` / 개별 스프라이트(lazy). 서비스워커는 페이지·데이터를 네트워크 우선, 스프라이트를 캐시 우선으로 나눴다.

**결과** — 초기 전송 3.0MB → 1.2MB, 첫 목록 표시 1.47s → 1.05s(CPU 4× 스로틀 기준). CI에는 스프라이트 캐시를 붙여 배포 시간도 줄였다.

</details>

### 2.2 D-MAX 티어를 커뮤니티 기준에 맞춤 (v2.0.1)
**문제** — 자체 공식으로 만든 티어가 이용자가 참고하는 pogomate와 어긋나 "이 표 맞아?"가 반복됐다.

**분석** — pogomate를 역산해 보니 내구를 빼고 **공격 × 맥스무브 위력 × 자속(1.2)** 만 쓰고, 다이맥스와 거다이맥스를 분리하고 있었다. 우리 표는 (a) 내구를 섞었고 (b) 타입 탭을 "그 타입을 보유한 종"으로 나눠 할비롱(드래곤 맥스무브)이 노말 탭에 올라와 있었다.

**결정** — 공식을 pogomate와 동일하게 맞추고, 타입 탭 분류 기준을 **그 타입 맥스무브를 쓰는 딜러**로 바꿨다. 연격의 우라오스처럼 이중 자속인 종은 양쪽 탭에 각각 표시하고 전체 탭에서만 중복을 제거한다.

**결과** — 노말·물·불꽃·풀·격투 상위권이 pogomate와 ±2%p 안에서 일치. 판단 근거(점수 분해)를 행 펼침에 노출해 다음 이견은 화면 안에서 확인 가능하게 했다.

</details>

<details>
<summary>2.2.1 다시 내구를 넣고, 등급을 전 종 절대 기준으로 (v3.30.0)</summary>

### 2.2.1 다시 내구를 넣고, 등급을 전 종 절대 기준으로 (v3.30.0)
2.2 의 결정(내구를 빼고 pogomate 와 같은 공식)을 **두 군데 되돌렸다**. 지금 동작은 이 절이 기준이다.

**문제 ①: 등급이 탭마다 달랐다** — `rel_tier` 가 넘겨받은 목록 안에서 상위 12% 를 S 로 잘랐다. 같은 점수 84,840 이 바위 탭(7행) 1위라 S, 땅 탭(9행) 2위라 S, 전체 탭(약 160종 중 상위 30만 실림) 30위라 C. 탭을 옮기면 글자가 바뀌고, 잘린 목록 탓에 어느 글자도 실력을 뜻하지 않았다.

**문제 ②: 화력만 본 표가 실제와 어긋났다** — 같은 화면의 딜러 표는 `dmg × √bulk` 인데 티어표만 `공격 × 위력 × 자속` 이었다. 그래서 1진화 몰드류(공 213 · 내구 23)가 2진화 거대코뿌리(공 202 · 내구 34) 위에 섰다. 맥스 배틀은 버티면서 맥스 페이즈를 여러 번 도는 싸움이라 내구가 실제 성능에 영향을 준다.

**결정** — `absolute_tier()` 가 `rel_tier` 를 대신한다(D-MAX 한정. PvE 일반 티어표는 상대 기준 그대로다). 전 종 1위 점수 대비 **90% 이상 S · 80% 이상 A · 70% 이상 B · 그 아래 C**, `dmax_all` 직후 **한 번만** 부른다. 점수에는 `(방어 × 체력 ÷ 1000) ** 0.25` 를 곱한다.

**왜 0.25 인가** — 제곱근(0.5)은 내구가 너무 세져 탱커 표와 구분이 사라지고, 0.25 는 진화 단계가 뒤집힌 것만 바로잡는 정도다. 내구 34 와 23 의 1.5배 차이가 보정에서는 2.42 와 2.19 의 1.1배로 줄어든다.

**결과** — 땅 1위 거대코뿌리 A(83%) 204,900, 2위 몰드류 B(79%). 바위 탭에서도 같은 A(83%) 로 글자가 유지된다. 전체 분포 S 8 · A 12 · B 10. 전체 28~30위 세 종(킹크랩·라이코·거대코뿌리)이 84,840 으로 같던 동점도 풀렸다. pogomate 와 순서가 갈리는 자리가 생기지만, 그 이유(내구 반영)를 카드 근거 두 줄과 표 제목 옆 `ⓘ` 에 적어 화면 안에서 확인할 수 있게 했다.

### 2.3 일정표는 "전 세계"가 아니라 "한국" (v1.3.x~)
**문제** — 글로벌 이벤트 데이터를 그대로 넣었더니 한국에 없는 레이드(레지 계열)가 표에 남고, 한국 전용 이벤트는 빠졌다.

### 2.4 솔플 계산기: 이론값에서 실측 보정으로 (v1.x~v2.x)
**문제** — 초기 계산은 "친구를 부르라"는 결론만 냈다. 실제로는 혼자 잡히는 레이드가 있었다.

<summary>2.5 "출시 여부"를 한 소스에 맡기지 않음</summary>

### 2.5 "출시 여부"를 한 소스에 맡기지 않음
**문제** — 게임마스터에는 미출시 콘텐츠가 미리 들어 있어 없는 포켓몬이 순위에 오른다. 그래서 PvPoke의 `released`로 걸렀는데, 이번엔 메타몽·껍질몬 같은 실제 출시 종이 도감에서 [미구현]으로 표시됐다.

**원인** — PvPoke의 `released`는 "PvP에서 쓸 수 있는가"에 가까운 플래그다. 대체 소스(pogoapi.net)는 네트워크 정책상 사용 불가.

**결정** — `PvPoke released ∪ 수동 화이트리스트`(`backend/config/dex_released_extra.txt`, 15종)로 합쳤다. 다이맥스 출시 목록도 같은 이유로 Bulbapedia 기준 수동 관리(`max_released.txt`).

**같은 함정을 두 번 더 밟았다 (v3.28.3 · v3.31.0)** — 둘 다 "게임 파일에 종족값이 있다 = 출시됐다" 로 읽은 자리다.

| 판 | 무엇이 잘못 떴나 | 왜 | 지금 기준 |
|---|---|---|---|
| v3.28.3 | 다이맥스 **두랄루돈** 이 '맥스 배틀 가능' | 게임마스터에 거다이맥스 **기술** 데이터(`SOURDOUGH_MOVE_MAPPING_SETTINGS`)가 있는 것을 다이맥스 출시로 착각 | `max_released.txt` 의 활성 줄만 인정. 확신이 없으면 '예정' 블록에 둔다 |
| v3.31.0 | 메가 **폭타** 가 도감 딱지에 | `pokemonSettings.tempEvoOverrides` 에는 미출시 메가의 종족값도 들어 있다 | PvPoke `gm.json` 의 **폼별** `released` → `names.py mega_released[(도감번호, 라벨)]` → `megas[].rel` |

**규칙** — 종족값은 "계산할 수 있다" 는 뜻이지 "나왔다" 는 뜻이 아니다. 출시 여부는 **별도 소스**에서 온다. 미출시인 것은 지우지 말고 `미구현` 으로 밝혀 둔다 — 지우면 왜 없는지 아무도 모르고, 밝혀 두면 데이터가 이미 있다는 사실까지 전해진다.

**v3.36.0 — 그 규칙을 D-MAX 표까지 넓혔다.** 도감·검색·상세 진화 칸만 지키고 있던 것을 순위표에도 적용한다.

| | |
|---|---|
| 무엇을 "데이터가 있다" 로 보나 | ① 게임마스터에 거다이맥스 **기술 데이터**가 있는데 출시 목록에 없는 종 ② `max_released.txt` 의 '예정' 블록 주석 줄 ③ PvPoke 출시 목록에 없는 메가(`megas[].rel === false`). **종족값은 근거가 아니다** — 그걸로 판정하면 전 종이 걸린다 |
| 보이는 모양 | `opacity: .55` + 왼쪽 점선 + `[미구현]` 딱지. 순위 칸은 번호 대신 `–` |
| 순위·등급 | 번호는 출시분끼리만 센다. 등급 100% 기준도 출시분 1위 — 미구현은 100% 를 넘을 수 있다 |
| 넣지 않는 곳 | 덱 짜기 후보 · 솔플 어태커 풀 · 홈 미리보기 · 추천 칩 · 활용처 집계. 표는 "있으면 이쯤" 이지만 그 다섯은 **지금 데려갈 수 있는 것**만 다룬다 |

같은 축을 하나 더 붙일 때도 이 네 칸을 그대로 채울 수 있어야 한다 — 특히 마지막 칸을 빼먹으면 "못 쓰는 것을 추천하는" 화면이 된다.

**v3.37.0 — 보일지 말지를 사람이 고르게 했다.** 늘 보여 주니 티어표 맨 위 여섯 줄이 전부 못 쓰는 것이었다. 머리의 `[ ] 미구현` 체크로 켜고 끄고, **기본은 꺼짐**이다(`pogo_max_unrel`). 켜면 오른쪽으로 물리고(`4.8rem` · 휴대폰 `2.2rem`) opacity `.4` + `blur(0.7px)` 로 더 갈라 놓되, hover·focus·펼침에서 풀린다. 카드 보기에서는 밀지 않는다 — 칸 폭이 정해져 있어 밀면 그 카드만 좁아진다. 거르는 곳은 `maxVisible()` 한 군데다.

**v3.38.0 — 회원 전용으로 좁혔다. v3.40.0 부터는 관리자 전용, v4.0.1 부터는 실험 기능이다.** 판정 하나(v3 `maxUnrelAllowed()` · v4 `beta`)를 체크·목록·안내 붙임말 셋이 본다. 비로그인에게는 체크를 아예 안 그리고, 기기 저장값이 켜져 있어도 목록에서 걸러진다. 로그인이 끝나면 D-MAX 를 다시 그린다(`auth.js onAuthChange`) — SDK 가 첫 렌더 뒤에 로드되므로 그러지 않으면 회원이 주소로 바로 들어왔을 때 자리가 안 생긴다(v2.49.0 잠긴 화면과 같은 함정).

> **이건 화면을 가리는 것이지 데이터를 막는 것이 아니다.** 순위표는 `dist/index.html` 에 통째로 심기는 공개 값이라 개발자 도구로 그대로 읽힌다 — `auth.js` 머리말의 "접근 제어의 주체는 이 화면 코드가 아니다" 와 같은 전제다. 진짜로 막으려면 미구현 줄을 빌드에서 빼고 로그인 뒤 Firestore 에서 받아야 한다.

<summary>2.5.1 관리자를 한 명에서 여럿으로 (v3.40.0)</summary>

### 2.5.1 관리자를 한 명에서 여럿으로 (v3.40.0)
**요구** — "로그인 한 유저를 내가 관리자로 지정할 수 있는 UI가 필요해."

**전** — 관리자는 `ADMIN_UID` 하나였다. `backend/build.py`(화면)와 `firestore.rules`(실제 권한) 양쪽에 같은 uid 가 박혀 있고, 늘리려면 코드를 고쳐 다시 배포해야 했다.

**결정** — 관리자를 **둘로 가른다.**

| | 어디에 | 누가 바꾸나 |
|---|---|---|
| **루트 관리자** | `firestore.rules` 의 `__ADMIN_UID__` (빌드의 `ADMIN_UID` 와 같은 값) | 아무도 못 바꾼다 — 잠금 방지용 열쇠 |
| **위임 관리자** | `allowlist/{이메일}` 문서의 `admin: true` | **루트만** 화면에서 지정·해제 |

**v4.0.1 — 관리자와 실험 참가자를 갈랐다.** `admin` 하나가 유저 관리에 더해 🎒 내 포켓몬과 D-MAX `[미구현]` 까지 열고 있었다 — 실험 기능을 보여 주려면 유저 목록을 함께 넘겨야 했다는 뜻이다. 반대편 구멍이 더 컸다: 패널의 `🧪 실험 기능` 버튼이 `beta: true` 를 적기만 하고 **읽는 곳이 한 군데도 없었다.**

| 깃발 | 여는 것 |
|---|---|
| `admin` | 유저 관리 — 승인된 사람 목록 · 트레이너 코드 관리 |
| `beta` | 실험 기능 — 내 포켓몬 · D-MAX `[미구현]` |

잠금 판정(`lib/useLocked.ts`)은 참·거짓 대신 **까닭**을 돌려준다(`login` · `beta`). 승인까지 끝낸 사람에게 "로그인하면 열려요" 를 내밀지 않기 위해서다.

**판정을 쓰는 자리는 넷이다** (v4.2.2 에 하나 늘었다).

| 자리 | 잠겼을 때 |
|---|---|
| 화면 본문 (`App` 의 `Screen`) | `LockCard` 로 바꿔 그린다 |
| ☰ 메뉴 줄 · PC 사이드바 | 흐려지고 라벨 뒤에 🔒 |
| 서비스 홈 타일 | 흐려지고 이름 뒤에 🔒 |
| **계정 카드의 `[🎒 내 포켓몬 N마리]`** | **줄째 사라진다** |

앞 셋은 "있다는 것과 지금은 못 쓴다는 것" 을 함께 보여 줘야 해서 남긴다. 계정 카드는 이동 목록이 아니라 **내 계정 요약**이라, 못 여는 것의 개수를 세어 보여 주면 "담아 둔 게 있는데 왜 못 보지" 가 된다. 이 넷째 자리가 v4.2.2 전까지 판정을 안 봐서, 실험 기능을 해제해도 셈 줄이 남아 있었다 — v4.0.1 버그와 같은 모양(규칙은 맞는데 읽는 사람이 빠짐)이다.

**v4.2.0 — 권한을 탭 복귀 때 다시 읽는다** (`stores/auth.ts recheckAccess`). 승인을 내리거나 거둬도 그 사람의 탭이 열려 있으면 판정은 로그인 때 읽은 그대로라, 새로고침 전까지 예전 권한이 남았다. `visibilitychange` 에서 `allowlist/{이메일}` **하나만** 다시 읽는다 — `applyUser` 를 부르지 않는 까닭은 저것이 가입 요청 문서를 쓰고 GA 에 `login` 을 찍기 때문이다. 탭을 오갈 때마다 그러면 한 사람의 로그인이 하루 수십 건이 된다. 같은 이유로 한 번 읽으면 1분 쉰다.

**읽기에 실패하면 아무것도 바꾸지 않는다.** 이를 위해 실패를 삼키지 않는 `getDocStrict` 를 어댑터에 따로 뒀다 — 기존 `getDoc` 은 못 읽어도 `null` 이라 '문서가 없다'(승인 해제)와 '못 읽었다'(회선 문제)가 같은 답이 된다. 그대로 썼으면 지하철에서 회선이 끊긴 사람이 화면에서 쫓겨난다. 실패하면 마지막 판정을 그대로 두고 계정 카드에 재시도만 안내한다(`recheckError`).

관리자가 **자기 권한**을 바꾼 경우에는 탭 복귀를 기다리지 않고 그 자리에서 다시 읽는다(v4.2.2, `AdminPanel` 의 `write(…, mine)`). 남의 권한을 바꾸는 경우는 그쪽 브라우저가 돌아올 때 스스로 읽는다.

**v3.41.0 — 권한도 갈랐다.** 처음에는 위임 관리자도 가입 승인을 할 수 있었다(`admin` 필드만 못 건드렸다). 누가 이 서비스를 쓰는지 정하는 일은 주인의 몫이라 좁혔다.

| | 루트 | 위임 |
|---|:---:|:---:|
| 가입 승인 · 승인 해제 · 관리자 지정 | ✅ | ❌ |
| 유저 목록 보기 · 트레이너 코드 · `[미구현]` | ✅ | ✅ |

규칙은 `allowlist` 의 `create`·`update` 를 `isRootAdmin()` 으로 좁히고, `requests` 는 **읽기 자체를** 루트만 하게 했다 — 승인할 수 있는 사람만 대기 목록을 읽을 이유가 있다. 화면도 그에 맞춰 메뉴 이름을 가른다: 루트 `🔑 가입 승인`, 위임 `👥 유저 관리`. **없는 권한을 이름으로 약속하지 않고, 눌러도 안 되는 버튼을 두지 않는다.**

**`admin` 필드를 루트만 건드리는 이유** — 위임 관리자가 또 다른 관리자를 만들 수 있으면 권한이 스스로 번지고, 루트를 끌어내릴 수도 있으면 되돌릴 사람이 없어진다. 규칙에서 `create` 는 "admin 을 켜지 않은 문서만", `update` 는 "admin 값을 바꾸지 않는 수정만", `delete` 는 "admin 이 아닌 사람만" 으로 막는다(본인 문서 삭제 = 계정 삭제는 그대로).

**화면은 규칙을 따라 적을 뿐이다** — `AUTH.adminRoot` 가 false 면 지정 버튼을 그리지 않지만, 그건 안내일 뿐이고 막는 것은 규칙이다. 우회해서 눌러도 `permission-denied` 로 실패한다.

> ⚠️ **규칙을 콘솔에 다시 게시해야 동작한다.** `scripts/render_rules.sh` 로 `firestore.rules.local` 을 만들어 Firebase 콘솔 > Firestore > 규칙에 붙여넣고 게시한다. 게시 전에는 [관리자 지정] 이 `permission-denied` 로 실패한다 — 화면에 그 오류를 그대로 띄운다.

<summary>2.7 로그인: 서버 없이 승인제 (v2.2.0)</summary>

### 2.7 로그인: 서버 없이 승인제 (v2.2.0)
**요구** — 구글 계정만 허용하고, 관리자가 승인한 사람만 쓰게 한다. 즐겨찾기는 계정에 저장해 기기를 바꿔도 유지한다.

### 2.10 CI가 조용히 실패하던 문제 (v2.3.0)
**증상** — 배포가 계속 실패하는데 로컬 빌드는 정상.

**원칙** — 외부 의존은 반드시 "실패를 실패로 드러내되, 배포는 막지 않는" 형태로 감싼다.

### 2.11 시즌 기술 조정을 "예측"이 아니라 "사실"로 다루기 (v2.5.0)
**상황** — 2026-09-08 황혼의 발자취 시즌에 기술 위력 27건이 조정되고 43종이 새 기술을 얻습니다. 티어표가 크게 흔들릴 예정이라 "상향 예정 ^ / 하향 예정 v" 뱃지를 붙이자는 요청이 있었습니다.

**따져 본 것** — 우리 파이프라인은 게임마스터에서 기술 위력을 읽어 DPS를 직접 계산하고 PvP는 PvPoke 랭킹을 받아옵니다. 즉 **적용일이 지나면 티어표는 손대지 않아도 자동으로 바뀝니다.** 그렇다면 "상향 예정" 뱃지는 (1) 적용 전 나흘만 쓸모 있고, (2) 순위가 실제로 오를지는 추측이며, (3) 시즌마다 손으로 붙였다 떼야 합니다.

**결론 — 시점을 둘로 나눴습니다.**

| 시점 | 표시 | 근거 |
|---|---|---|
| 적용 전 | `9/8 기술↑` 예고 뱃지 + ⚔️ 기술 변경 페이지 | 공지된 사실(어떤 기술이 몇에서 몇으로) |
| 적용 후 | `▲3 · ▼5` 변동 뱃지 | 직전 빌드 순위와 비교한 실제 결과 |

예측은 어느 쪽에도 넣지 않았습니다. 적용 전에는 "무슨 기술이 어떻게 바뀐다"만, 적용 후에는 "실제로 몇 계단 움직였다"만 말합니다. 덕분에 변동 뱃지 쪽은 이번 시즌용이 아니라 **모든 시즌에 계속 작동하는 상시 기능**이 됐고, 손이 가는 부분은 시즌마다 `move_changes.txt` 한 파일을 갈아끼우는 것뿐입니다.

**적용 범위 함정** — 공지의 위력 수치는 **트레이너 배틀(PvP) 값**입니다. 게임마스터는 같은 기술이라도 레이드·체육관용 위력(`moveSettings.power`)과 배틀용 위력(`combatMove.power`)을 따로 갖고 있고, 시즌 조정은 보통 후자만 건드립니다. 이번 공지의 '이전 값'이 전부 `combatMove` 쪽과 일치하는 것으로 확인했습니다(아이언헤드 공지 70 → 레이드용 60·배틀용 70, 땅고르기 공지 45 → 레이드용 80·배틀용 45). 레이드·체육관까지 바뀌면 공지가 그렇게 따로 밝히며, 이번에는 사이코부스트(70 → 130) 하나뿐입니다. 그래서 안내 화면 첫 줄에 "PvP 기준"임을 못박아 뒀습니다 — 이게 없으면 "아이언헤드가 85인데 왜 레이드 순위가 그대로냐"는 질문이 나옵니다.

**부수적으로 정한 것**

- 변동 2계단 미만은 기록하지 않습니다. PvPoke 랭킹은 매일 ±1 정도 흔들려서, 다 표시하면 뱃지가 상시 표시가 되고 정작 큰 변화가 묻힙니다.
- 순위가 실제로 달라진 빌드에서만 스냅샷을 갱신합니다. 화면만 고쳐 다시 빌드하는 일이 잦은데 그때마다 갱신하면 변동이 0으로 지워집니다.
- 비교 키는 `스프라이트|이름`입니다. 섀도우와 일반은 같은 그림(같은 스프라이트 id)을 써서 id 만으로 묶으면 섀도우의 변동이 일반 쪽에 붙습니다.
- 기록 후 14일이 지나면 뱃지를 감춥니다. 두 달 전 변동이 붙어 있으면 "최근 변동"이라는 뜻이 사라집니다.

### 2.13 아머드 뮤츠가 통째로 빠져 있던 문제 (v2.7.0)
**증상** — 게임마스터에도 PvPoke에도 데이터가 있는데 검색·도감·순위표 어디에서도 안 나왔다.

**원인 두 겹**

1. 게임마스터 폼 표기가 `MEWTWO_ARMORED`가 아니라 **`MEWTWO_A`**다. `FORM_KO`에는 `'armored'`만 있어 `label_from_gm()`이 `None`을 돌려줬고, `pve_build.py`가 "라벨 표에 없는 폼(코스튬 등)"으로 보고 후보에서 제외했다.
2. PokeAPI `pokemon.csv`에 **`mewtwo-armored` 행 자체가 없다**. 그래서 `sprite_id()`가 기본 폼 번호(150)를 돌려준다.

**1번을 고칠 때의 함정** — `FORM_KO`에 `'a'`를 넣으면 접미사가 같은 **안농(`UNOWN_A`)이 전부 "아머드 안농"**이 된다. 그래서 접미사 표가 아니라 종까지 함께 보는 `GM_FORM_EXCEPTIONS`에서 처리했다.

**2번은 그림 문제가 아니라 신원 문제** — 번호가 겹치면 도감 폼 표·기술 변경 영향 표·맥스 배틀 표에서 일반 뮤츠와 같은 칸을 써 서로를 덮어쓴다. 그래서 `sprite.py`에 **저장소가 직접 배정하는 번호(`LOCAL_FORMS`, 90000번대)** 를 두고, 그림은 기본 폼 png를 복사해 쓴다(`sprites.py`). 전용 일러스트가 생기면 그 파일만 갈아 끼우면 되고 번호 체계는 그대로다. 90000번대를 고른 이유는 PokeAPI id가 10000번대까지라 겹칠 일이 없어서다.

**그림 (v2.7.2 추가)** — v2.7.0에서는 일반 뮤츠 png를 복사해 써서 화면에서 둘이 같아 보였다. PokeAPI에는 없지만 **포켓몬 GO 게임 에셋(PokeMiners/pogo_assets)** 에는 폼별 아이콘이 있어(`Images/Pokemon/Addressable Assets/pm<도감번호>.f<폼접미사>.icon.png`, 아머드는 게임마스터 표기 `MEWTWO_A`를 따라 `pm150.fA`) `sprite.py`의 `LOCAL_SPRITE_URL`에 주소를 적어 두면 `sprites.py`가 내려받는다. 실패하면 원본 복사로 폴백한다. 주의할 점 둘: (1) CI의 `actions/cache`가 v2.7.0 시절 복사본을 되살리므로 "파일이 있으면 통과"가 아니라 **원본과 바이트가 같으면 다시 받는다**로 판정한다. (2) 이 아이콘은 96px 픽셀 아트가 아니라 3D 렌더라 `.sprite`의 `image-rendering: pixelated`로 축소하면 계단이 진다 — `sprite.js`가 90000번대에 `sprite-hd`를 붙여 `auto`로 그린다.

`dex.json`의 `dex` 매핑에도 `90150 → 150`을 직접 넣었다. 이게 없으면 프런트 `dexOf()`가 원종을 못 찾아 진화 단계·즐겨찾기 ★·활용처가 통째로 사라진다.

### 2.15 뒤로가기가 팝업을 닫게 (v2.11.0)
**증상** — 폰에서 상세 팝업이나 ☰ 메뉴를 연 뒤 뒤로가기를 누르면 팝업이 닫히는 게 아니라 이전 페이지(또는 사이트 밖)로 갔다. 페이지(`#/dex` 등)는 해시라 뒤로가기가 됐지만, 오버레이는 DOM만 띄우고 히스토리에 아무것도 남기지 않았기 때문이다.

**결정** — 오버레이를 처음 열 때 `history.pushState`로 항목을 **하나** 넣고, 닫힐 때 그 항목을 되돌린다(`components/history.js`). 원칙 셋: (1) 사용자의 뒤로가기(popstate)는 열린 것을 전부 닫는다. (2) X·Esc로 닫으면 DOM을 먼저 지우고 `history.back()`으로 항목을 되돌린다. (3) 팝업 위에서 다른 팝업을 열거나 드로어에서 팝업으로 넘어갈 때는 항목을 재사용한다(silent 닫기). 항목을 재사용하지 않고 열 때마다 push하면 뒤로가기를 여러 번 눌러야 하고, 닫을 때마다 back하면 "드로어 닫기 → 팝업 열기"처럼 연달아 일어나는 동작이 비동기 back과 경합한다.

**페이지 이동 함정** — 팝업이 열린 채 `#/dex`로 가면 히스토리에 "닫힌 팝업" 항목이 남아 뒤로가기가 그 항목(주소만 같은 빈 화면)에 한 번 걸린다. 그래서 오버레이가 열린 상태의 해시 이동은 `location.replace`로 그 항목을 덮어쓴다(`navigateHash`). `openPage`·`openTypeSearch`는 반드시 이 함수를 거친다.

### 2.19 클래스 이름 규칙 — BEM, 최대 3단어 (v2.24.0)
**문제.** 클래스 이름이 세 시기의 규칙을 섞어 쓰고 있었다. 축약(`d-head` · `psearch` · `acct-danger` ·
`lbl` · `crit`), 의미 없는 접두사(`g-S` · `s-0` · `x2` · `r2`), 그리고 같은 단어가 두 층을 동시에
가리키는 경우(`overlay` = 바깥 `<dialog>`, `modal` = 안쪽 카드)까지. 이름만 봐서는 어느 컴포넌트에
붙는지, 블록인지 요소인지 알 수 없었다.

**규칙.** `block-name__element--modifier`.

| 자리 | 뜻 | 예 |
| --- | --- | --- |
| `block` | 혼자 설 수 있는 덩어리 | `home` · `search` · `drawer` · `plan` |
| `__element` | 그 블록 안에서만 뜻이 있는 부분 | `home__tile` · `search__head` · `modal__close` |
| `--modifier` | 같은 블록·요소의 변형 | `tabs__item--quick` · `filter-box--search` · `plan__status--a` |

- 단어 구분은 `-` 하나만. `_`(단독)·camelCase 를 쓰지 않는다
- 이름 전체는 **최대 3단어** (`badge-main__prev` 가 상한). 넘으면 블록을 새로 판다
- 여러 블록이 함께 쓰는 상태는 요소가 아니라 **`is-*` 유틸리티** — `is-on` · `is-high` ·
  `is-unreleased` · `is-weak2` · `is-resist2` · `is-up` · `is-down`. 한 블록에만 붙는 상태는 `--modifier`
- **코드가 문자열로 만드는 클래스도 같은 규칙**을 따른다. 대소문자·숫자를 그대로 이어 붙이면
  CSS 와 어긋난다 (`` `g-${letter}` `` 는 `g-S`, CSS 는 `.g-s` 였다). 지금은 매핑 배열을 거친다 —
  `grade-mark--s` · `plan__status--a`

**바꾸지 않은 것.** 전역 이름 · `state` 키 · **DOM id** · localStorage 키 · GA 이벤트명 · Firestore
필드명은 불변 규칙이라 그대로다. `#tabs` · `#page` · `#search-dialog` 같은 id 선택자는 리팩토링
전후가 같다.

**확인 방법.** 순수 이름 변경은 "테스트가 통과한다"로는 부족하다. 22개 화면 × 두 폭(390 · 1440)에서
`getComputedStyle` 지문을 뜨되 **클래스 이름을 지문에서 뺐다** — 태그·깊이·44개 계산 속성만 남긴다.
리팩토링 전후 지문이 같으면 이름만 바뀌고 렌더는 그대로라는 뜻이다.

**일정표는 왜 자동화하지 않았나.** 같은 저장소가 이벤트도 주지만 **영문 원제뿐**이다. 지금 일정표는 한국
공식 발표를 보고 한글로 적은 것이라, 자동 수집으로 바꾸면 품질이 내려간다. 데이터는 `GAMEDAY.events` 로
실어 두되 화면에는 붙이지 않았다. 필드 리서치도 같은 이유로 보류했다 — 과제 문구가 영문 문장이다.

**넣지 않은 것.** GO로켓단 라인업은 자동 수집원이 없어 사람이 매번 적어야 한다. 일정표에서 없애려던 바로
그 구조라 넣지 않았다.

### 2.22 `overflow-x: auto` 는 세로축도 함께 적는다 (v2.26.0)
**증상.** PC 에서 순위 화면이 스크롤되지 않는다는 제보. 그런데 주소로 바로 들어가면 잘 굴러가고,
자동화로 훑어도 멀쩡했다. 재현 조건은 **커서 위치**였다 — 커서가 탭 줄 위에 있을 때만 막혔다.

**원인.** CSS 규칙상 한 축이 `visible` 이 아니면 **나머지 축의 `visible` 은 `auto` 로 계산된다.**

```css
.tabs { overflow-x: auto; }   /* → overflow-y 도 auto. 세로 스크롤 컨테이너가 된다 */
.tabs__item { border-bottom: 2px solid transparent; margin-bottom: -1px; }  /* 1px 삐져나옴 */
```

선택된 탭의 밑줄이 컨테이너 테두리를 덮으려고 1px 위로 올라와 있었다. 그 1px 때문에 탭 줄은
"세로로 스크롤할 게 있는 영역"이 되고, 브라우저는 커서 아래 스크롤 컨테이너를 먼저 소비한 뒤
남는 만큼만 페이지로 넘긴다. 1px 은 순식간에 끝나지만 **그 뒤로도 페이지로 넘어가지 않는다.**

PC 에서만 드러난 이유는 배치다. 즐겨찾기 카드가 커서 탭 줄이 화면 한가운데로 내려왔고,
마우스 커서가 자연히 그 위에 놓였다. 모바일은 손가락으로 본문을 직접 굴려 드러나지 않았다.

**규칙.** 가로 스크롤 줄에는 **`overflow-y: hidden` 을 반드시 함께 적는다.** 세로로 넘칠 일이
없어 보여도 그렇다 — 테두리·그림자·포커스 링·음수 여백이 1px 을 만든다.

이번에 함께 고친 곳: `.tabs` · `.chips` · `.boss__recs` · `.priv__table-wrap`.
`.tabs` 는 음수 여백 대신 컨테이너 테두리를 `inset` 그림자로 바꿔 넘침 자체를 없앴다(겉모습 동일).

**검사 방법.** `tests/e2e/shell.js` 가 화면마다 모든 요소를 훑어 `overflow-y` 가 `auto`/`scroll`
이면서 넘침이 **24px 이하**인 것을 찾는다. 일부러 긴 상자(팝업 본문·드로어·사이드바)는 넘침이
크므로 걸리지 않고, 이런 사고성 1~2px 만 잡힌다.

<summary>2.23 스크롤 잠금은 상태에서 끌어낸다 (v2.26.0)</summary>

### 2.23 스크롤 잠금은 상태에서 끌어낸다 (v2.26.0)
**문제.** 오버레이를 열 때 `document.body.style.overflow = 'hidden'`, 닫을 때 되돌리는 방식이었다.
여는 자리 3곳 · 닫는 자리 3곳에 흩어져 있었고, 닫는 경로를 **하나라도 놓치면 잠금이 남는다.**
남으면 페이지가 영영 스크롤되지 않고 사용자가 되돌릴 방법이 없다 — 새로고침뿐이다.

**해결.** 잠금을 명령이 아니라 **상태의 결과**로 만든다.

```js
function overlayVisible() { return !!document.querySelector('dialog[open]'); }
function syncScrollLock() { document.body.style.overflow = overlayVisible() ? 'hidden' : ''; }
window.addEventListener('hashchange', syncScrollLock);
window.addEventListener('popstate', syncScrollLock);
window.addEventListener('pageshow', syncScrollLock);
```

- 팝업·드로어·검색이 모두 `<dialog>` 라 **브라우저가 관리하는 `open` 하나**만 보면 된다.
  우리 쪽 표시(`hidden` 속성 등)를 믿으면 갱신을 놓칠 때 어긋난다
- 화면이 바뀔 때마다 다시 맞추므로 **놓쳐도 다음 이동에서 저절로 풀린다**(자가 복구).
  버그가 나도 사용자가 갇히지 않는다는 것이 이 구조의 요점이다

**곁다리로 드러난 것.** `drawer.css` 가 `header { display: flex }` 로 모든 `<header>` 를 잡고 있었다.
작성자 규칙은 브라우저 기본값 `[hidden] { display: none }` 을 **이긴다.** 그래서 `hidden` 을 붙여도
감춰지지 않았다(v2.26.0 화면별 헤더가 여기 걸려 모바일에서도 보였다). 선택자를 좁히고,
`base.css` 에 `[hidden] { display: none !important }` 안전망을 뒀다. 태그 선택자로 `display` 를
거는 규칙은 언제든 이 사고를 다시 만든다.

### 2.24 정적 사이트에서 막을 수 있는 것과 없는 것 (v2.27.0)
GitHub Pages 는 **응답 헤더를 못 바꾼다.** 그래서 흔히 권하는 방비의 절반은 여기서 쓸 수 없다.
할 수 있는 것만 정직하게 하고, 못 하는 것은 언제 가능해지는지 적어 둔다.

| 방비 | 지금 | 이유 |
| --- | --- | --- |
| CSP | ✅ `<meta>` | 헤더만큼은 아니지만 **외부 도메인 주입은 막힌다** |
| Referrer-Policy | ✅ `<meta>` | meta 로 지원되는 몇 안 되는 헤더 |
| HSTS · X-Frame-Options · X-Content-Type-Options | ❌ | 헤더 전용. 커스텀 도메인 + CDN 이후 |
| 요청 수 제한 | ❌ | 서버가 없다. CDN 단계에서만 가능 |
| Firestore 쓰기 한도 | ✅ 규칙 | **여기가 진짜 공격면이다** — 아래 참고 |

**CSP 에 `'unsafe-inline'` 이 들어가는 이유.** 번들이 인라인 `<script>` 한 덩어리다(빌드가 파일을
합친다). 그래서 인라인 실행 자체는 막지 못한다. 그래도 값이 있다 — `script-src` 에 적힌 출처
말고는 **외부 스크립트를 못 불러온다.** 공격자가 어떻게든 마크업을 심어도 `<script src="악성.com">`
은 브라우저가 거부한다. 덧붙여 `object-src 'none'`(플러그인) · `base-uri 'none'`(`<base>` 로 모든
상대경로를 남의 서버로 돌리는 수법) · `form-action 'none'`(폼이 없는 사이트라 전부 차단).

**진짜 공격면은 Firestore 다.** 정적 파일은 읽기 전용이라 훔칠 것이 없다. 쓰기가 가능한 곳은
Firestore 뿐이고, 승인된 사용자가 실수하거나 계정이 털리면 **문서 하나로 무료 한도를 태울 수 있다.**
클라이언트의 `PLAN_MAX_MONS` 검사는 우회되므로 규칙에서 막아야 의미가 있다.

**규칙에서 필드 이름을 못 박지 않는다 (`hasOnly` 의 함정).**
`set({ merge: true })` 는 `request.resource.data` 가 **기존 + 새 값을 합친 결과**다.
예전 버전이 남긴 필드가 목록에 하나라도 없으면 그 사용자는 **그때부터 아무것도 저장하지 못한다.**
되돌리려면 규칙을 다시 게시해야 하고, 그 사이 사용자는 이유도 모른 채 저장이 안 된다.
그래서 이름 대신 **개수와 크기**로 막는다 — `keys().size()` · 목록 길이 · 문자열 길이.

실제로 이번에 `hasOnly` 를 먼저 썼다가, 코드가 쓰는 필드를 전수 확인해 보니
`requests` 의 `status`·`consentAt` 과 `users` 의 `name` 이 빠져 있었다. 그대로 게시했으면
**로그인이 통째로 막혔다.** 규칙을 조일 때는 반드시 쓰는 쪽을 먼저 전수 확인한다.

### 2.26 v4 화면 규칙이 v3 스킨을 이기는 장치는 하나 (v4.4.0)

흐린 글자 · 선 · 강조 · 주 버튼)을 쓴다 — 테마와 무관하므로 다크 블록에 다시 적지 않는다.

### 2.27 성능 — 자리를 먼저 지키고, 데이터를 먼저 받는다 (v4.4.2)
**먼저 잰다.** 느낌으로 고치면 한 군데를 빠르게 하고 다른 군데를 느리게 한다(v4.4.2 에서 그 일이 있었다 —

| 도구 | 무엇을 | 언제 믿나 |
| --- | --- | --- |
| `scripts/check_perf.mjs <주소> [<주소>]` | 실제 조절(4G · CPU 4배)로 본문이 보이기까지 · CLS 와 출처 · 긴 작업 | **배포된 두 주소를 나란히** 잴 때. 판정은 사람이 |
| `npx lighthouse … --only-categories=performance` | 큰 방향(무엇이 LCP 인가 · 어느 자원이 막나) | 같은 빌드가 2.6s ↔ 5.4s 로 흔들린다 — 숫자로 판정하지 않는다 |
| 소스맵(`vite build --sourcemap`) | 청크에 무엇이 들었나 | 청크 이름만 보고 믿지 않는다 — `react` 청크가 4KB 였다 |

**자리를 먼저 지킨다 (CLS).** 데이터 뒤에 포털로 들어오는 것(머리 단추 줄 · 순위 셸의 탭·필터)은 빈 채로도
높이를 지킨다(`routes.ts` 의 `actions` · `surfaces.css`). Suspense 의 스플래시는 한 화면을 채운다 — 바닥글이
먼저 보였다가 밀리면 그것이 CLS 다. 출처를 모르면 `check_perf.mjs` 가 `layout-shift` 의 노드를 찍어 준다.

**정적인 것은 기다리지 않는다.** 화면 맨 위에서 데이터 훅을 부르면 글자뿐인 머리까지 기다린다 — 히어로는 바로,
데이터가 필요한 아래만 `<Suspense>` 로(`Home` / `HomeData`). 없어도 되는 곁줄은 `bundleSoftHook`(기다리지 않는
`useQuery`)으로 — 키·해시가 `bundleHook` 과 같아 캐시를 나눠 쓴다.

**긴 목록은 `content-visibility: auto`.** 화면 밖 카드의 스타일·레이아웃·그리기를 건너뛴다.
`contain-intrinsic-size: auto <높이>` 로 스크롤 막대를 잡는다. **검문의 눈을 가린다** — 건너뛴 카드는 `innerText` 에
안 잡히므로 `check_screens` · `check_contrast` 는 훑기 전에 `content-visibility: visible` 을 잠시 켠다.
새 검문을 만들면 같은 줄을 넣는다.

**첫 화면이 반드시 쓰는 데이터는 HTML 이 먼저 받는다.** `finalize-html.mjs` 가 빌드 때 manifest 의 해시를 읽어
`dex`·`meta` 를 `<link rel=preload as=fetch crossorigin>` 으로, 화면별 묶음은 주소창 해시를 보는 한 줄로 건다.
주소는 `lib/data.ts` 와 글자 하나까지 같아야 한다 — 콘솔에 "preloaded but not used" 가 뜨면 짝이 안 맞는 것이다.

### 2.28 기록할 자리를 만든다 — 화면은 그대로 정적 (v4.7.2)
**문제.** GA4 가 우리 데이터를 안 돌려준다. v4.6.3 에서 검색순위를 내린 진짜 이유가 트래픽이 아니라
GA4 의 성질이었다 — 세 가지가 겹친다.

| GA4 의 성질 | 우리에게 생기는 일 |
| --- | --- |
| Data API 는 **집계만** 돌려준다 | 원본 이벤트를 못 꺼낸다. 다시 세어 볼 수가 없다 |
| 지역 측정기준이 섞이면 방문자 적은 행을 **제 임계값으로 숨긴다** | 나라별 순위가 구조적으로 비어 온다 (v4.6.0 에서 이미 부딪혔다) |
| 기본 보존 **14개월** | 지금 쌓는 `search` 는 2027년 말에 사라진다 |

하루 3회짜리 검색어는 우리 표에서는 정확히 3 이지만 GA4 에서는 영영 안 보인다.
쌓고 있는 것이 우리 것이 아니라 **구글이 빌려주는 요약본**이라는 것이 문제의 전부다.

**검토.** 셋을 놓고 쟀다.

| 안 | 되나 | 왜 안 골랐나 |
| --- | --- | --- |
| GA4 → BigQuery 일일 익스포트 | **된다.** 무료이고 원본 이벤트를 준다 | 목적이 셋(내 DB · 백업 · 구직)인데 세 번째를 전혀 못 채운다. 데이터만이 목적이면 이쪽이 더 쌌다 |
| 화면을 SSR 로 옮긴다 | 된다 | 지금 자산을 통째로 버린다 — 첫 화면 278KB(gz) · PWA 오프라인 · GitHub Pages 무료 · 재방문 전송량 0. 없는 것은 '기록할 자리' 하나뿐인데 전부를 바꿀 이유가 없다 |
| 정적 사이트 옆에 수집기 한 대 | 된다 | **골랐다.** 바꾸는 것이 '기록' 하나다 |

**결정.** `server/` 에 Node 서버 한 대. 맡는 것과 안 맡는 것을 못 박는다.

- **맡는다** — 이벤트 수집(`POST /v1/events`) · 일별 집계 · 순위 조회 · (3판) Firestore 백업 미러
- **안 맡는다** — 로그인·권한은 Firebase Auth 와 `firestore.rules` 그대로다. 검증된 규칙을 직접 짠 JWT 로 갈아엎는 것은 리스크만 크다
- **화면은 이 서버를 런타임에 안 읽는다.** 보내는 쪽만 붙었다(`lib/collect.ts`, 실패를 삼킨다).
  순위를 다시 올릴 때도 빌드가 `GET /v1/hot` 을 받아 정적 파일로 굽는다 — 그래야 서버가 죽어도 화면이 선다

**설계 원칙 §1 을 고쳤다.** "서버를 두지 않는다" 는 이제 참이 아니다. 말없이 깨면 문서가 거짓말이 되므로
**"화면에는 서버를 두지 않는다 · 기록은 서버가 맡는다"** 두 줄로 갈랐다.

**오염을 막는 것이 이 판의 진짜 일이다.** 수집 엔드포인트는 공개라 누구나 밀어 넣을 수 있다.
겹을 다섯 두되, 마지막 겹 하나만으로도 버티게 했다 — **사람당 한도**(`PERSON_CAP=5`)가 있으면
한 사람이 같은 말을 천 번 보내도 5 로 잘린다. 반대쪽은 v4.6.0 의 문턱이 그대로 막는다.
겹 전체는 [`server/README.md`](../server/README.md#데이터-처리-원칙) 에 있다.

**CORS 는 그 다섯에 없다.** CORS 는 브라우저가 *응답을 읽는 것*을 막을 뿐이고,
`sendBeacon` 이 보내는 단순 요청(`text/plain`)은 프리플라이트 없이 그냥 도착한다.
그래서 `Origin` 헤더를 **서버가 직접 본다**. 이걸 검사로 못 박아 뒀다(`남의 사이트에서 쏜 beacon 은 403`).

**개인정보.** IP 는 어디에도 저장하지 않는다 — 앞단이 판정해 둔 국가 코드만 읽으므로 이 서버는 IP 를 볼 일조차 없다.
방문자는 브라우저가 만든 난수(`pogo_visitor`)이고, `pogo_consent=denied` 면 한 건도 안 나간다(GA4 와 같은 게이트).

**설명서는 코드에서 뽑는다.** 주소마다의 모양은 라우트의 JSON Schema 에 이미 있으므로
`@fastify/swagger` 가 그대로 읽는다 — 손으로 쓰면 언젠가 어긋나고, 어긋난 설명서는 없느니만 못하다
(읽는 사람이 그걸 믿고 짠다). 저장소의 `openapi.json` 과 [`docs/server-api.html`](server-api.html) 은
`npm run openapi` 가 굽고, **검사가 코드와 파일을 대어 본다**. 표 그림도 같은 규칙이다 —
[`server-erd.html`](server-erd.html) 을 고치고 `node scripts/bake_erd.mjs` 로 다시 굽는다.

**결과.** 1판은 화면에 보이는 변화가 없다. `search` 이벤트가 GA4 와 내 DB 에 **나란히** 쌓이기 시작할 뿐이다.
둘을 견줄 수 있는 동안 내 수집기가 맞는지 확인하고, 2주쯤 쌓인 뒤에 v4.6.3 이 내린 검색순위를
`ranking` 브랜치에서 되살린다 — 그때는 GA4 의 임계값이 없다.

### 2.16 배틀 유형별 참전 풀 · 리전 폼 자격 · 탱커 축 (v2.13.0)
**참전 풀(QA-49)** — "원시 가이오가 보스에 다이맥스 추천이 나온다"는 보고. 조사해 보니 D-MAX 티어표와 보스 딜러 목록(`DMAX_DATA`)은 이미 `max_released` 기준으로 걸러져 있었고, 실제 누수 지점은 **상세 팝업의 "보스로 나오면?"** 이었다. 이 섹션은 보스 종류와 무관하게 대표 타입의 맥스 배틀 딜러만 보여 줬다. 맥스 배틀에는 다이맥스·거다이맥스 가능 포켓몬만, 일반·전설·메가 레이드에는 전체가 들어간다는 자격 규칙을 여기서 갈랐다: 보스 이름이 다이맥스/거다이맥스로 시작하면 맥스 딜러, 아니면 상성표에서 배율 1.6 이상인 공격 타입(최대 2개)의 레이드 성능표 상위 5(종 중복 제거). 계획했던 `maxEligible` 플래그 주입은 필요 없었다 — 데이터가 아니라 화면 조립 경로의 문제였다.

**리전 폼 자격(QA-50)** — 위 조사 중 발견. `in_release_set`의 마지막 항("폼 정보가 없으면 그 종이 어떤 폼으로든 등재돼 있으면 인정")이 아니라 두 번째 항 `(pokemon_id, None) in release_set`이 문제였다. 관동 파이어 한 줄로 `MOLTRES_GALARIAN`까지 통과해 미출시 리전 폼 9건이 티어표에 올랐다. 새 규칙에서 까다로운 건 **기본 폼 항목이 어느 줄에 대응하느냐**다. 우리 `pve_full meta`는 스트린더의 하이한/로우한, 불비달마의 STANDARD를 따로 갈라 두지 않아 '스트린더' 한 항목이 두 폼을 대표하는데, 설정 파일에는 `D TOXTRICITY TOXTRICITY_AMPED`처럼 폼까지 적혀 있다. 그래서 "기본 폼 항목은 폼 없음/`X_NORMAL` 줄, 그리고 **우리 데이터에 따로 없는 폼**의 줄과 같다"(`base_form_matches`)로 정했다. 리전 폼(`MOLTRES_GALARIAN`)은 데이터에 따로 있으므로 기본 폼이 대표하지 않는다. 결과 다이맥스 139·거다이맥스 17(공식 17종과 일치).

**탱커 축(QA-43)** — pogomate는 딜러 표와 탱커(EHP) 표를 따로 둔다. 우리는 "이번 주 보스 아코디언"이 이미 있으니 두 축을 **파티 카드(딜러 2 + 탱커 1)** 로 합쳐 보여 주는 쪽이 친구들 질문("뭘 데려가?")에 가깝다. 탱커 지표는 체력 × 방어 ÷ 1000 ÷ 받는 배율로, 배율은 보스가 자기 타입 자속 기술로 때린다고 가정한다(복합 타입 보스는 근사치 — 각주로 밝혔다). 순위표 자체는 [딜러 | 탱커] 세그먼트 뒤에 두고, 파티 카드의 탱커는 딜러와 종이 겹치지 않게 고른다. (v2.14.0 QA-52: 세그먼트를 [전체 | 딜러 | 탱커]로 늘려 전체 = 티어표, 딜러 = 보스 상대 어태커, 탱커 = EHP 로 축마다 표 하나씩. 속성 칩은 세그먼트 아래 하위 메뉴 줄에 라벨과 함께.)

**활용 N곳(QA-42)** — `VALUE_DATA.usage`는 상위 80만 실어 뱃지 원천으로 쓰기엔 모자랐다. 전 항목의 등재 내역을 `usage_places`(이름 → [[곳, 순위]], 329개 약 20KB)로 압축해 따로 싣고, 모든 순위표가 거치는 `row()`에서 자동으로 붙인다. 상세 팝업 활용처(`usagePlacesFor`)도 이 데이터를 읽게 바꿔, 뱃지 숫자와 팝업 칩 개수가 같은 목록에서 나온다 — 예전엔 팝업이 상위 80만 봐서 81위 밖 포켓몬은 활용처가 통째로 비었다. 1곳짜리는 붙이지 않는다 — 모든 행에 붙으면 뜻이 없다.
