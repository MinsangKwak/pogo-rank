# 로그인과 권한 — 서버가 하는 일

[← 서버 스키마](SCHEMA.md) · [고도화 계획](../docs/ROADMAP.md)

**2026-09-22 v5 Phase 4 에 Firebase Auth 가 하던 일을 여기로 가져왔다.**
왜 가져오나 — JWT · 세션 · 인가를 다룬 자리가 코드에 없으면, 그 일을 할 줄 안다고 말할 근거도 없다.

---

## 1. 흐름 한 장

```
브라우저                     우리 서버                      구글
   │                            │                            │
   │ GET /v1/auth/google/start  │                            │
   ├───────────────────────────►│ state·nonce·PKCE 검증자를 만들어
   │                            │ 서명한 쿠키에 담는다 (10분)
   │◄───────────────────────────┤ 302
   │                            │                            │
   │ 구글 로그인 화면 ──────────────────────────────────────►│
   │◄────────────────────────────────────────────────────────┤ 302 + 인가 코드
   │                            │                            │
   │ GET …/callback?code&state  │                            │
   ├───────────────────────────►│ ① 쿠키를 열어 state 를 견준다
   │                            │ ② 코드+검증자를 토큰으로 바꾼다 ──►│
   │                            │◄───────────────────────────┤ id_token
   │                            │ ③ 서명·발행자·**수신자**·**nonce** 를 다시 본다
   │                            │ ④ users 에 upsert, sessions 에 한 줄
   │◄───────────────────────────┤ 302 + 리프레시 쿠키 (httpOnly)
   │                            │
   │ POST /v1/auth/refresh      │
   ├───────────────────────────►│ 회전: 옛 줄에 used_at, 새 줄 발급
   │◄───────────────────────────┤ 액세스 토큰 (답 본문으로만)
```

---

## 2. 왜 이렇게 했나

### 인가 코드 흐름 + PKCE

암묵적 흐름은 토큰을 **주소로** 받는다. 주소는 브라우저 기록 · 리퍼러 · 서버 로그 셋에 남고
셋 다 우리가 못 지운다. 인가 코드는 한 번 쓰면 죽고, 그것을 토큰으로 바꾸는 일은 비밀번호를 쥔
서버만 한다 — 브라우저는 토큰을 구경도 못 한다.

PKCE 는 비밀번호가 서버에만 있으니 이론상 없어도 된다. 그래도 쓰는 이유는 **코드가 가로채여
우리 콜백보다 먼저 도착하는 경우**다. 검증자를 모르면 코드만으로는 아무것도 못 한다.

### 콜백이 토큰을 안 준다

구글에서 돌아온 브라우저에는 **쿠키만** 심고 앱으로 보낸다. 앱이 그 쿠키로 갱신을 한 번 불러
액세스 토큰을 받는다. 토큰을 주소에 실으면 위의 셋에 그대로 남는다.

### 서명이 맞다고 우리에게 온 것은 아니다

`id_token` 은 구글이 서명한 값이지만, **다른 앱에 발급된 것**일 수 있다. `aud` 를 안 보면
아무 구글 앱의 토큰으로 우리 서비스에 로그인할 수 있다 — 이 흐름의 고전적인 구멍이다.
그래서 넷을 본다: 서명 · 발행자 · **수신자(aud)** · **우리가 낸 nonce**.

### 회전과 사슬

리프레시는 한 번 쓰면 새것으로 갈린다. 이미 쓴 것이 또 오면 둘 중 하나다 —
네트워크가 답을 잃어 같은 것을 두 번 보냈거나, 누가 훔쳐 갔거나. **구분할 방법이 없으므로
그 사슬(`family_id`) 전체를 끊는다.** 훔친 쪽도 원래 쪽도 다시 로그인해야 한다.
불편하지만, 훔친 쪽만 조용히 살아 있는 것보다 낫다.

기기마다 사슬이 따로 선다 — 폰에서 토큰이 새도 PC 는 계속 쓴다.

### 액세스 토큰은 짧고 얇다

15분. 이름도 이메일도 안 담는다 — 담은 값은 만료 전까지 못 무른다.
권한이 바뀌면 **다음 회전에** 따라오고, 즉시 끊어야 하는 일은 사슬을 끊는 쪽이 맡는다.

### 잠금 방지 열쇠가 환경변수다

`ROOT_EMAIL` 로 로그인하면 언제나 루트다. 끌어내려져 있어도 로그인에서 되돌아온다.
전에는 이것이 Firestore 규칙 본문의 uid 였다 — 누구도 못 뺏지만, 고치려면 **콘솔에 게시**해야 했다.
코드 배포와 따로 도는 절차라 잊기 쉬웠다.

## 3. 무엇을 안 담나

- **IP 를 어느 표에도 안 담는다** (CLAUDE.md §3). 수집 서버에만 하는 약속이 아니다.
  `sessions.user_agent` 는 사용자에게 '어디서 로그인했나' 를 보여 주는 용도다.
- **리프레시 토큰 원문을 안 담는다.** `sha256` 만 둔다 — DB 가 통째로 새도 남의 세션으로 못 들어온다.
- **구글의 리프레시 토큰을 안 받는다** (`access_type=online`). 세션은 우리가 돌린다.
  안 쓸 비밀은 안 받는 것이 제일 싸게 지키는 길이다.

## 4. 주소

| 주소 | 무엇 | 문 |
| --- | --- | --- |
| `GET /v1/auth/google/start` | 구글 화면으로 보낸다 | 누구나 |
| `GET /v1/auth/google/callback` | 인가 코드를 받는다 | 구글 |
| `POST /v1/auth/refresh` | 쿠키 → 액세스 토큰 | 쿠키 |
| `POST /v1/auth/logout` | 이 기기만 끊는다 | 쿠키 |
| `POST /v1/auth/logout-all` | 모든 기기를 끊는다 | 토큰 |
| `GET /v1/auth/sessions` | 어디서 로그인했나 | 토큰 |
| `GET /v1/me` | 내 정보 | 토큰 |
| `DELETE /v1/me` | 계정 삭제 — **줄 하나** | 토큰 |

권한은 `pending` · `approved` · `admin` · `root` 넷이고, 판정은 `lib/rbac.ts` **한 곳**에서만 한다
(Firestore 는 규칙의 다섯 함수와 화면 코드 두 벌이었다).

## 5. 검사

```bash
cd server
TEST_DATABASE_URL=postgres://…/moncamp_test npm test
```

| 파일 | 무엇 | 수 |
| --- | --- | --- |
| `rbac.test.ts` | 권한 판정이 규칙과 같은 답을 내는가 | 7 |
| `jwt.test.ts` | **위조를 거부하는가** — alg:none · 알고리즘 바꿔치기 · 본문 손대기 · 남의 열쇠 | 13 |
| `google.test.ts` | 구글이 맞다고 한 것을 우리가 얼마나 다시 보는가 | 19 |
| `auth.test.ts` | 로그인 · 회전 · **사슬 끊기** · 계정 삭제 (진짜 Postgres) | 31 |
| `authroutes.test.ts` | 토큰이 주소에 안 실리는가 · 쿠키가 httpOnly 인가 · 열린 리다이렉트 | 21 |

**검사를 먼저 썼고, 그 값이 바로 나왔다.** 구멍 둘이 여기서 잡혔다 —
① 재사용을 잡고도 트랜잭션이 되감기며 사슬이 되살아나던 것,
② 같은 이메일에 다른 구글 계정이 오면 500 이 나던 것.

**검사가 실재하는지도 확인했다.** `algorithms: ['HS256']` 과 `audience` 를 각각 빼 보고
해당 검사가 빨개지는 것을 봤다 — 통과만 보고 넘어가면 아무것도 안 재는 검사가 생긴다.
